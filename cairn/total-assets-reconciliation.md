# 總資產對帳（三本帳一致性）

## 背景

**2026-09-13 實案**：VM 上 2395、3665 各 36 股**只寫進 `logs/performance.csv`**，沒進 `logs/holdings.json` 與分帳本（成本基礎缺口 92,484）。

兩個後果：

1. 總資產口徑 A（`core/drawdown_guard.compute_equity`，股災防護用）低估 91,764。
2. **這種部位永遠不會被賣掉**——賣出與孤兒清倉只認 `holdings.json`。

同一案還有第二個坑：分帳本路徑曾被寫錯 ⇒ `cost=0` ⇒ 算出 **2,055,586** 的荒謬總資產。所以「缺檔」若回退成 0 靜默通過，錯誤比直接報錯更危險。

## 當前結論

三本帳，各有單一權威：

| 帳 | 檔案 | 角色 |
|---|---|---|
| 成交紀錄 | `logs/performance.csv` | append-only，券商回報後寫入 |
| 目前持股 | `logs/holdings.json` | **所有賣出／孤兒清倉的唯一依據** |
| 分帳本 | `logs/stock_allocation.json` | 成本基礎（算 `avg_cost`／資金上限） |

三個總資產口徑（`scripts/reconcile_total_assets.py`）：

- **A 現金流**（MDB 股災防護用）＝ `TOTAL_CAPITAL + (ΣSELL − ΣBUY) + Σ(holdings.json 股數 × 現價)`
- **B 儀表板**＝ `TOTAL_CAPITAL + FIFO已實現 + (持股市值 − 分帳本成本)`
- **C CSV 自洽**＝ `現金 + Σ(CSV FIFO 未平倉股數 × 現價)`

**A 與 B 的代數關係**：`B − A ≡ Σ未平倉成本基礎(CSV FIFO) − Σ分帳本成本基礎`（因為 `FIFO已實現 = 淨現金流 + Σ未平倉成本基礎`）。

⚠️ **2026-11-05 更正（原寫「帳務一致時 A ≡ B」不精確）**：兩個成本基礎的**費用口徑不同**——
`core.books.fifo_open_positions()` 的成本**含買進手續費**（2026-09-17 起），而實盤 `stock_allocation.total_buy_cost`
是 `px × 股數`（`selfselect_trader.py` 的 `_led['total_buy_cost'] += trade_cost`，**不含費用**）。
⇒ 即使三本帳完全同步，`B − A` 也會等於「**未平倉部位的買進手續費合計**」（實測 2026-11-05 為 **+1,070**）。

逐檔驗證（2026-11-05 修帳後）：

| 代號 | FIFO 成本（含費） | 分帳本成本（不含費） | 差 |
|---|---:|---:|---:|
| 2603 | 251,242.00 | 250,884 | +358 |
| 2609 | 250,356.00 | 250,000 | +356 |
| 2408 | 250,244.00 | 249,888 | +356 |
| 2615 | 117,667.50 | 117,667.50 | 0（補帳時分帳本採 FIFO 口徑） |
| **合計** | **869,509.50** | **868,439.50** | **+1,070** |

（三檔的買進手續費各約 356–358 ✔；2603 的分帳本成本 250,884 略高於 25 萬上限＝實際成交金額，正常。）
判讀方式：`✅ 三本帳一致`（股數與檔案自洽）＋ `B − A` 應為**小額正向**且能用「持倉買進手續費」解釋；
若差距大到不是費用等級（或方向為負），才是真的不同步。部位比對由 `core/books.py` 提供（**唯一實作**）。

### 口徑 D（2026-11-11 新增）：持倉報告的「總資產(持股+停泊)」

TG 持倉報告（`_build_holdings_message()`）尾端多一個**人眼總覽**用口徑：

```
總資產(持股+停泊): NT$1,027,420
合計未實現損益: -15,420（持股 -26,620｜停泊 +11,200）
```

- **A／B／C 都不含停泊**：停泊交易寫 `logs/park_trades.jsonl`、**不在** `performance.csv`
  ⇒ `compute_equity()` 的「現金」實際上把停泊成本（195,200）當現金（沒有扣、也沒有加市值）。
- 因此 `D − A ≈ 停泊未實現損益`（實測 11/11：+11,200）。**D 只用於人眼看總覽，不進任何風控判斷。**
- 開放問題：股災防護（A 口徑）要不要也把停泊市值算進去？現在它低估/高估的幅度＝停泊未實現損益，
  停泊部位大時（本專案常態 20%～40%）不是小數字。要改就得先決定停泊在「現金」與「部位」之間算哪一種。

設計原則（`core/books.py`）：

- 檢查**不需要現價、不需要網路**（純比對股數與成本）⇒ 可以每個迴圈跑。
- 缺檔（分帳本／持股檔不存在）一律視為**不一致**，不回退成 0。
- `holdings` 是記憶體快照：與磁碟不同 ⇒ 別的 writer 寫過 ⇒ 下一次 `save_holdings` 會把對方成交**整份蓋掉**（lost update）⇒ 必須告警。

## 券商庫存對帳的證據上限（2026-11-05 首跑實測）

首次在 v1.1.29 容器跑 `scripts/reconcile_broker_books.py`（唯讀），輸出：

```
⚠️  券商回傳只有 1 檔（疑似僅涵蓋當日成交／未交割）；本機另有 3 檔未涵蓋、無法比對：2408, 2603, 2609（完整庫存請以券商對帳單為準）
✅ 三本帳與券商一致
```

- **這個 ✅ 不是「券商端沒問題」**：它只證明 ①本機三本帳自洽 ②**唯一**被回傳的那 1 檔與帳本相符。
  3 檔（11/03 買進、11/05 T+2 交割）根本沒進回傳 ⇒ 「有沒有更早的殘留部位」仍是未知。
- 原因：模擬環境 `get_inventories()` 只回「當日有成交」的標的（`data/esun_provider.query_inventories` 註解、
  2026-09-23 實測），結算後持股不會出現；`get_transactions_by_date` 對歷史日期也回空
  ⇒ **SDK 在模擬環境無法列完整集保庫存**。
- ⇒ 「券商端還有沒有舊部位」只能用**券商 App／網頁庫存頁或月對帳單**確認；SDK 能做的只有
  「當日成交的即時對帳」。`ESUN_ENVIRONMENT=real` 是否同樣受限＝**未驗證**，真錢上線前要實測一次並記錄。
- 實務規矩：回報對帳結果時，**警告那一行必須一起講**，不要只貼最後的 ✅
  （否則就是拿部分證據下全域結論——和 `backtest-data-pitfalls.md` 的「資料覆蓋率」問題同一類）。
- 這次的 `--json`：`rows: []`、`consistent: []`，`logs/holdings.json` ＝
  `{2603: 909, 2609: 4000, 2408: 608, 2615: 0}`。**兩張清單都空 ⇒ 那 1 檔回傳股數是 0**
  （`consistent` 只在股數 > 0 時才列），多半就是當天成交的 2615 ⇒ 券商端 2615 已無「未交割」部位。
- ~~工具缺口~~ **已修（v1.1.30）**：`--json` 與文字報告都帶 `broker_symbols`（含 0 股列，例 `2615(0 股)`），
  並補一條 note「…股數為 0（＝當日已無未交割部位；不代表沒有更早的舊部位）」。
  ⇒ 之後看輸出就能自己說清楚「回傳 0 檔」vs「回傳 1 檔但 0 股」，不必再靠 `snapshot_broker.py` 反推。

## 更正：2026-11-05 的快照證據（原文的推論要修）

同一天先看 `reconcile_broker_books.py --json`（`rows`／`consistent` 都空）時推論「券商端 2615 已無部位、
疑慮偏向不存在」——**不成立**。`scripts/snapshot_broker.py` 的原始回傳顯示：

| 欄位 | 值 |
|---|---|
| `transactions` | 只有 1 筆 `S 2615 1,000 股 @114.00`（fee 162、tax 342、`c_date=20261109`） |
| `inventories` 2615 | `qty_b=0`／`qty_s=2000`／`qty_sm=1000`／`stk_dats=[]`／`value_now=0` |

⇒ **帳本記「賣出 2,000 股」，券商實際只成交 1,000 股**（帳本 2615=0）。

補查 `get_settlements()` 只有一筆 `{c_date: 20261109, date: 20261105, price: 113496}`（＝11/05 賣 1,000 股的交割款），
**11/03 買進當天已交割、已不在清單** ⇒ 交割明細只能確認賣出那半，買進股數要靠券商 App／對帳單。

**模擬帳沒有「看得到」的介面（2026-11-05 使用者確認）**：玉山 App 不吃模擬環境的 API key ⇒ 沒有庫存頁／對帳單可看，
模擬帳的證據**只存在 SDK 回傳**，而 SDK 只看得到「當日成交」與「未交割明細」。
⇒ 「11/03 買進到底成交幾股」在模擬帳**永遠查不到**；`inventories` 那列的 `value_now=0` 也**不能**當「0 股」的證據
（該列只涵蓋當日成交符號，`stk_dats` 是空的，值是骨架不是餘額）。

**因此決定（依 `core/broker_sync` 的既有不對稱政策）**：帳本照**硬證據**修——11/05 的 SELL 是 1,000 股、費用 504；
一旦 SELL 改成 1,000，FIFO 未平倉就是 1,000 股，三本帳要一致就只能把 `holdings`／分帳本補回 1,000 股
（「賣出少成交 ⇒ 補回」＝保守方向，最壞情況是少賣一次，不是重複建倉）。
若哪天券商端其實是 0 股，會在**下次 2615 出現賣訊**時露出來（成交短少或拒單），屆時用同一支工具
`--allow-trim` 反向修即可。

**處置（v1.1.32）**：`scripts/broker_shortfall_repair.py --snapshot logs/broker_snapshot_2026-11-05.json`
（dry-run 先看）→ `--apply` 會把 11/05 的 SELL 改成 1,000 股、`cost` 改成券商實收 504，
並用修正後的 CSV 重算 FIFO ⇒ `holdings` 2615 回到 1,000 股、分帳本同步。**先確認券商端是否還有那 1,000 股**
（券商 App／對帳單）再按下去；若券商端其實是 0 股，就要另外減帳而不是補回。

推理上的旁證：13:27 的賣單 2,000 股能被他方接受並**部分成交 1,000**，代表當時集保至少 2,000 股
（券商一般不會接受超過庫存的現股賣單）⇒ **券商端很可能仍有 2615 1,000 股**；但模擬環境是否驗證庫存＝未知，
仍以券商畫面為準。

兩個教訓：

1. **`inventories.qty_b=0` 不等於「沒有部位」**：在「當日有成交」的列上，它可能被圈存／交割中抵掉。
   要判「有沒有那一千股」只能看交割明細或券商畫面。
2. **`broker_sync` 抓的是「當日成交」，救不了歷史落差**：模擬環境 `get_transactions_by_date` 對過去日期回空，
   所以「今天只成交一半」若沒當天補帳，隔天就查不到證據 ⇒ 快照必須每天落地（v1.1.25 的理由再確認一次）。

## 教訓

- **缺口不會自己消失**：只寫進 CSV 的部位在報表上看得到、卻永遠不會被賣出。發現帳不平要當天補，不要等月底。
- **fail-loud 勝過 fail-silent**：缺檔回退成 0 會製造一個「看起來很合理」的錯誤總資產。
- **lost update 是靜默的**：兩個 writer 同時持有記憶體快照時，後寫的會整份覆蓋先寫的；`holdings` 與磁碟不一致就是這個訊號。
- **修帳要留人工關卡**：對帳工具一律唯讀，改動一律先 dry-run、先備份、留稽核軌跡。
